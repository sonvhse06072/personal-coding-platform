## Direction A — scoped execution boundary (NOT an active topology)

Only on Owner's existing WSL host and subject to separately approved activation:

1. **Datastore:** a brand-new G0-only PostgreSQL service/volume (candidate names `pcp-g0d01-postgres` / `pcp-g0d01-postgres-data`), never the currently running legacy `personal-coding-platform-postgres`, no data copy from PCP's durable historical jobs, no import/migration, no published DB host port.
2. **Registry:** Runtime/Router/Executor will eventually receive only `pcp-g0-drupal-fixture` from `config/g0-fixture-only/projects.yml`. Baselines are an exact subset of the approved immutable revision in `config/g0-fixture-only/project-baselines.yml`; PM Bridge registry is empty. Do not mount the canonical full `config/projects.yml` or any legacy project control/lease records in the new instance.
3. **Workspaces / DDEV:** workspace namespace `pcp-g0d01` and dedicated G0 container network `pcp-g0d01-private`; frozen seed and a unique DDEV project ID for the PCP arm. Direct arm must have a *different* workspace/DB identity, same CLI/model/effort/source/acceptance digest. Do not touch active Codex's direct Chợ Nhạc worktree, DDEV project or global Codex binary.
4. **Services and privileges:** staged mode has `runtime_startup_mode=inspect`; **all execution-related activation flags remain false**. No new executor with host Docker socket, no host Antigravity bridge, no PM Bridge polling, no n8n, no GitHub delivery, no automatic merge, no fixture `ddev start`. During any later active phase, a project-scoped Executor/host capability contract must be implemented and verified independently of the in-process allowlist.
5. **Host coexistence:** sharing Docker Desktop daemon/router is **not hard isolation**. A separate database/registry removes the strongest historical cross-project replay path but does not prove that a host-socket-owning Executor cannot affect another project. If scoped permissions / resource or router coexistence cannot be demonstrated, **keep PARKED** and return an explicit No-Go rather than try a speculative startup.

The new `config/g0-fixture-only/source-contract.yml` is **source-only planning data, not Docker Compose**. Other three files are PARKED mirrors, not applied to a deployed service. `scripts/g0-fixture-isolation-contract.py` checks their equality to canonical fixture source, frozen baseline, empty PM Bridge and the exact non-activating plan. Its default CLI only reads tracked files and emits sanitized PASS/STOP with `ready_to_dispatch_g0d_t01=false`. Negative tests intentionally fail on DDEV/delivery activation, registry widening, baseline drift, changed DB namespace or Docker-socket permission. CI PASS proves only source-contract consistency.

### Opt-in Executor API scope — source hardening (separate PR, not live)

The scoped Executor mode uses `PCP_EXECUTOR_PROJECT_SCOPE=pcp-g0-drupal-fixture`. Without that exact opt-in, existing Executor behavior remains unchanged. When opted in, a singleton fixture registry with the frozen project path, `benchmark/pcp` branch and isolated-clone mode is mandatory. All other project IDs are rejected before handler filesystem/DDEV operations. **The pre-activation HTTP allowlist contains only GET `/health`**, and this health response remains `degraded` without probing Docker, DDEV or Buildx. Even fixture-owned workspace creation, DDEV phases, delivery, generic job-ID-only `/v1/cancel`, orphan resource cleanup, PM GitHub bridge and all new endpoints are refused. Later fixture-owned operations require their own protected activation PR and ownership tests; scoped registration alone cannot perform work. Negative tests use mock inputs only.

**This is an application/API boundary, not an OS-level sandbox:** it does **not** restrict a future Executor's Docker-socket access, filesystem mounts, host project reachability, or indirect shared Docker/DDEV-router side effects. In particular, the currently denied unscoped cancel/orphan cleanup paths need fixture-owned job identity attestation before future active-execution support; never enable them globally merely to make G0 work. A separate protected decision and project-scoped host capability design are still prerequisites for actual startup/activation.

### Isolated G0 service topology — parked Compose candidate (not deployed)

`deploy/g0/compose.candidate.yml` specifies an independent `pcp-g0d01` Docker Compose namespace with a **new private PostgreSQL volume** (`pcp-g0d01-postgres-data`), **internal-only** `pcp-g0d01-private` network, and Router/Runtime/Executor containers using local images that must be explicitly selected and verified by the Owner. Every service is behind the non-default `owner-gated-g0` profile, `restart: no`, `pull_policy: never`, with no published host ports or shared host-DDEV hooks. All image references require explicit operator input; this source file does not build, pull, start or provision containers.

The candidate Router/Runtime/Executor receive the **fixture-only** project registry via read-only individual file binds, not the legacy canonical multi-project registry. The Executor sees only the exact fixture Git source (read-only) plus a dedicated new workspace bind, **no host Docker socket** or broad projects root. Runtime uses `inspect`, Executor uses opt-in scoped/PARKED health, and no host Codex/Antigravity/Git credentials are mounted. The private network is deliberately offline. Candidate static CI checks reject changing the namespace, port/network exposure, host mounts, privileges, profiles, activation and registry/scope. They do not establish that images are current, services start, or shared Docker resource pressure is acceptable.

**This candidate CANNOT execute G0D-T01:** no Docker socket, DDEV phases still disabled, no model/provider entitlement, no outbound network, no GitHub delivery and no job-execution authorization. It is a safe topology preparation only. To enter an active G0 phase, the separate protected proposal must resolve the precise project-bounded DDEV capability (e.g. private daemon/broker with enforceable scope, not a naked shared host socket), provision independent workspace/DB ownership, preserve rollback and negative tests, and establish provider/CLI/source/CI parity without touching Owner Codex or Chợ Nhạc.

### Owner-approved inspection-only activation — guarded WSL operator (2026-10-11)

The Owner separately approved an **inspection-only local creation/start** of new `pcp-g0d01` resources in [DEC-G0-INSPECTION-ACT-01](https://github.com/sonvhse06072/personal-coding-platform/issues/595#issuecomment-6107936724). This is narrower than enabling fixture execution, host Docker/DDEV capabilities or provider credentials. The previously merged source contract remains `PARKED` for jobs and G0D-T01.

`scripts/g0-inspection-operator.py` is the audited operator entrypoint and is **not invoked by GitHub CI**. Run it only from the Owner's WSL after a guarded clean Git fast-forward to the exact merged source. It has explicit commands:

- `preflight --expected-sha <exact-main-SHA>`: read-only checks: clean PCP `main` and frozen `benchmark/pcp` fixture clone with exact Git origins/SHAs; non-symlink config paths; static parked source contract, inspected Compose/profile/private network; sufficient WSL RAM/disk; all four G0 target container names, network, volume, service tags and aliases absent; three preloaded PCP base images and **local `postgres:17`** image present; `docker compose config --quiet`. No sources are fetched, built, pulled, changed or started by this command.
- `activate --expected-sha <exact-main-SHA>`: **rechecks all preflight conditions first**, then creates only new `pcp-g0d01-*` alias/overlay images offline from preloaded PCP service images. Each overlay copies the exact source `app/` into its image and labels the approved revision; no package install or network/image pull. Creates an owner-only `~/.pcp-g0d01/workspaces` and a private mode-0600 `owner-state.json` with fresh G0-only database password; the password is never logged. Uses exact Compose project/profile with `up --no-build --pull never --no-recreate --wait`; creates only the new scoped DB volume/network/services. Health checks use in-container loopback: PostgreSQL ready; Router health OK with protected route denied, Executor health degraded/health-only with fixture workspace POST denied, Runtime health degraded/inspection-only with job POST denied. Verifies G0 Compose labels, private network, absence of public ports/host Docker socket and dedicated DB volume.
- `status`: only verifies already-owned G0 service identities and inspection-only health, without starting/stopping anything.
- `stop`: stops **only** explicitly named and Compose-label-verified running G0 containers (including partial startups); it does **not** stop Docker/DDEV globally, restart legacy PCP, delete volumes, remove any project/workspace or touch Chợ Nhạc. Never retry an interrupted activation blindly; preserve partial evidence and diagnose first.

`postgres:17` is an explicit **preloaded-image** prerequisite, not an implicit pull: if missing, the script stops with `postgres17_not_cached_no_implicit_pull`. Similarly it fails closed for dirty/unmatched source, unavailable G0 names/resources, insufficient headroom, incompatible Compose, missing local base images or unexpected image provenance. G0 image tags are unique and do not overwrite the legacy PCP tags. A dedicated operator script with immutable expected HEAD and distinct preflight/start commands prevents accidental cross-environment invocation. No secrets or full external Docker logs are printed.

**Limits:** Successful `activate` proves only four G0 inspection services and data/network ownership. No real WorkOrder execution, no GitHub delivery, no provider/quota/model parity and no OS-isolated DDEV capability; old PCP PostgreSQL, leases and Chợ Nhạc must remain untouched. This is an Owner-operated local action: a ChatGPT GitHub-only session cannot attest it succeeded. After local PASS, separately review the protected fixture-only DDEV/host broker and explicit G0D-T01 permission contract. Do not interpret this section or source CI as actual rollout evidence.

## Next feature-critical choice — first G0D-T01 comparable developer loop

**Path CI-first (PM preferred for G0 only, needs explicit acceptance/governance decision):** The frozen fixture's [existing validation workflow](https://github.com/sonvhse06072/pcp-g0-drupal-fixture/blob/main/.github/workflows/validation.yml) already runs `composer validate --strict`, locked install, PHP lint, Drupal PHPCS, and real PHPUnit Unit/Kernel tests against its own isolated MariaDB service on GitHub-hosted Ubuntu, PHP 8.4. Keep **identical** workflow/acceptance policy for both `benchmark/direct` and `benchmark/pcp` arms and compare the full accepted-ticket→PR+CI+review cycle. This avoids exposing the shared WSL Docker socket or creating a bespoke local DDEV broker merely for G0 quality verification. It **does not** demonstrate local DDEV/preview parity (reserve that for G1); if the original controlled G0 cohort requires local DDEV on both arms, change the benchmark scope only by explicit Owner decision, with the limitation disclosed. The actual PCP developer still needs a scoped isolated workspace, real model/CLI entitlement, a source-pinned non-legacy Runtime enablement, and fixture-only GitHub PR delivery with protected authorization.

**Path local-DDEV:** Build a true project-owned DDEV execution capability for the G0 fixture while leaving the shared host Docker daemon unavailable to the agent/runtime. A mere HTTP allowlist, project registry or Docker socket proxy is **not hard OS isolation**. A bounded host broker with exact project/lease/command attestation has residual privileged-host risk; a separate daemon/runner has higher complexity/resource cost. Each requires its own Owner-approved trust-boundary ChangeProposal and real negative host-coexistence tests. Do not provision this just to bypass G0 unless the local developer feedback loop is an explicit G0 acceptance requirement.

**No automatic G0 permission follows from this design note.** Both routes still require equal source seed, same actual installed Codex CLI/model/reasoning effort, authenticated provider permission without copying the Chợ Nhạc session, per-arm distinct workspaces and databases, final deterministic/independent CI+review, and no mutation of either frozen benchmark branch before trials. G0 investment gate cannot claim p50/p90 with 0 accepted pairs.
