# Telegram Terminal Operations Gateway

Status: approved target design and operating convention. Not implemented yet.

This document records the approved direction for a separate owner-only Telegram interface that can run local diagnostics and, later, carefully bounded operational actions on the Human Owner's Ubuntu/WSL machine without turning Telegram into an unrestricted remote shell.

The existing PCP Telegram integration remains the governance/notification/control surface for Runtime decisions. The terminal operations gateway is a separate capability with a separate bot token and a separate trust boundary.

## 1. Interaction convention for ChatGPT/operator blocks

The default interaction does **not** change.

When ChatGPT provides a read-only diagnostic block during normal collaboration, it should continue to provide the same terminal-safe block format used today. The Human Owner can paste that block directly into the local terminal.

A Telegram-specific execution format is used **only when the Human Owner explicitly asks for a read-only block that is ready to send through Telegram**, for example by saying that the block should be "Telegram-ready", "sẵn sàng cho Telegram", or equivalent.

Therefore:

- ordinary read-only request -> ordinary terminal-safe shell block;
- explicit Telegram-ready read-only request -> Telegram execution metadata/format described below;
- do not automatically wrap every diagnostic block in Telegram metadata;
- do not require the Telegram gateway for normal local terminal work.

Existing terminal-safety conventions still apply to ordinary blocks:

- prefer readable heredocs over fragile nested quoting;
- avoid `python3 -c '...'` for non-trivial logic;
- do not give a top-level interactive block that can accidentally terminate the user's WSL shell through unwrapped `set -e` + `exit 1` behavior;
- use a child `bash <<'BASH' ... BASH` or equivalent when guarded failure is required;
- preserve explicit safety gates around active jobs, repository cleanliness, state-machine mutations and rollouts.

## 2. Architectural objective

The target owner workflow is:

```text
Human Owner on Telegram
        |
        v
Separate PCP Terminal Bot
        |
        +--> /run-ro  -> capability-restricted read-only runner
        |
        +--> /run-op  -> named bounded operation -> explicit confirmation
        |
        +--> /run-admin -> disabled by default
```

The bot must make it practical to paste a multi-line diagnostic block generated by ChatGPT and receive stdout/stderr back on Telegram while preserving strong local trust boundaries.

The design goal is **arbitrary diagnostic logic inside restricted capabilities**, not a text allowlist pretending to prove arbitrary shell code is safe.

## 3. Separate bot and identity boundary

The terminal bot should be separate from the existing PCP governance/notification bot.

Required boundary:

- separate Telegram bot token;
- owner-only access;
- private-chat-only access;
- require both the configured owner `from.id` and owner `chat.id` to match;
- reject group/channel use;
- never treat Telegram message text as trusted shell input merely because it came from the configured account;
- do not share Runtime/provider/GitHub/Docker secrets with the terminal bot unless a narrower brokered capability explicitly requires them.

Recommended transport for the first implementation is Telegram long polling so the local machine does not need a public inbound port or webhook. This is implementation guidance, not a requirement if a future deployment has a safer equivalent transport.

## 4. `/run-ro`: arbitrary diagnostic script in a capability-restricted sandbox

`/run-ro` is intended for the long read-only blocks commonly used during PCP diagnosis.

Example owner flow:

```text
/run-ro
<paste multi-line shell block>
```

The bot presents a preview/hash and then executes the block only inside the read-only runner.

The runner may support general shell/Python diagnostic logic, but its **capabilities** must enforce read-only behavior. Security must not depend on regex checks such as `if "rm " not in script` or a blacklist of command strings.

### Read-only filesystem shape

Target sandbox view:

```text
repository/source roots       read-only
PCP job workspaces            read-only
approved logs/status files    read-only
/tmp                          writable scratch only
secret files                  not mounted
Docker socket                 not mounted
SSH agent/socket              not mounted
```

The read-only runner must not have write access to source repositories, PCP durable job state, workspaces, host configuration, credentials or production resources.

### Environment boundary

Diagnostic scripts must not receive raw credentials such as:

- `RUNTIME_API_TOKEN`;
- GitHub delivery/merge credentials;
- provider API keys/tokens;
- Antigravity bearer/credential material;
- SSH credentials or `SSH_AUTH_SOCK`;
- unrestricted Docker/DDEV authority.

Environment variables should be scrubbed/minimized before execution.

### Command/capability examples

The read-only environment may support operations equivalent to:

- `git status`, `git diff`, `git log`, `git show`, `git grep`, `git ls-files`;
- process/port/system status inspection;
- bounded log reads;
- PCP job/plan/action/event/quota inspection through a read-only broker;
- safe Python used for parsing/formatting/comparison;
- SQL `SELECT` through a dedicated read-only database principal;
- other diagnostics whose underlying OS/container/database permissions make mutation impossible.

The following capabilities must remain unavailable in `/run-ro` regardless of script text:

- source/workspace writes;
- Git commit/checkout/reset/merge/rebase/push/force-push;
- Runtime control mutations;
- database `INSERT`/`UPDATE`/`DELETE`/DDL;
- Docker socket/container mutation;
- DDEV restart/rebuild with mutation authority;
- `sudo`/root escalation;
- arbitrary SSH;
- arbitrary production operations;
- direct secret reads;
- unrestricted external network egress unless a specific future diagnostic policy explicitly permits a narrow destination.

## 5. PCP read-only broker

Because many current diagnostics inspect Runtime internals using commands such as `ddev exec -s coding-runtime python3`, shell-text analysis cannot safely determine whether the embedded Python or SQL is truly read-only.

The target design therefore includes a small `pcp-readonly-broker` or equivalent local interface.

It exposes only bounded read methods such as:

```text
job(job_id)
jobs()
plan(plan_id)
actions(plan_id, work_order_id)
events(job_id)
quota()
git_status(project)
logs(component, bounded_range)
```

The read-only runner talks to this broker instead of receiving Runtime API credentials or database credentials with mutation authority.

The broker may internally hold the minimum credential needed to read Runtime state, but that credential is never exported to the diagnostic process.

### Database principal

If direct SQL inspection is needed, use a dedicated principal such as `pcp_observer` with only the minimum read grants required for the approved schema/tables.

Expected properties:

- database connection/use grant as needed;
- schema usage as needed;
- `SELECT` only on approved tables/views;
- no `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, DDL, ownership or role-management capability.

A mistaken or malicious diagnostic `DELETE` must fail at the database permission boundary rather than rely on parser detection.

## 6. `/run-op`: bounded operational actions

`/run-op` is a future layer for operations that intentionally mutate local platform state but are already represented by an approved bounded operation.

Examples may include:

- normal orchestrator tick;
- restart of the constrained Antigravity bridge;
- service-scoped Runtime rebuild/restart when the existing safe rollout gates permit it;
- execution of an already materialized Runtime control action through its official endpoint.

`/run-op` must **not** accept unrestricted arbitrary shell with elevated authority.

Instead, it should map to named operations whose implementation validates current state immediately before execution.

Every mutation should normally require an explicit Telegram confirmation button containing a one-time, short-lived operation identity/hash.

Example:

```text
⚠️ Restart Antigravity bridge?

[Confirm] [Cancel]
```

The operation must fail closed if the job/platform state changed between preview and confirmation.

## 7. `/run-admin`

`/run-admin` is disabled by default and is not required for the initial implementation.

High-authority actions should continue to require direct local/owner control unless a later, separately approved security design proves an equivalent boundary.

Examples that should **not** become generic Telegram terminal capability:

- unrestricted `sudo`;
- root shell;
- arbitrary Docker commands;
- arbitrary source-repository writes;
- force push;
- destructive database operations;
- raw secret inspection;
- production deployment/write operations;
- bypass of PCP Runtime/PM state-machine or governance gates.

## 8. Telegram-ready diagnostic block format

This format is optional and should be generated only after an explicit Human Owner request for a Telegram-ready block.

Recommended metadata shape:

```bash
# PCP-EXEC: readonly
# PCP-TTL: 30m
# PCP-ID: diag-20260915-001

bash <<'BASH'
set -euo pipefail
# diagnostic commands
BASH
```

The terminal bot may calculate/display a SHA-256 hash of the received block and show a preview before execution.

Useful properties:

- mode is explicit (`readonly`);
- TTL prevents old diagnostic instructions from being reused indefinitely;
- ID provides a human-readable audit/reference key;
- hash identifies the exact text executed;
- editing any line changes the hash and therefore requires a new confirmation/preview.

The metadata is an execution/audit aid, **not** the security boundary. The sandbox/broker permissions remain authoritative.

## 9. Output, timeout and audit policy

The terminal bot should enforce:

- one bounded execution timeout per request;
- maximum stdout/stderr size with truncation and explicit indication;
- bounded number of concurrent commands, initially one;
- serialization for mutating `/run-op` actions;
- audit record containing owner identity, Telegram message/update identity, execution mode, block hash/operation ID, timestamps, exit code and bounded result metadata;
- no raw secret values in logs or Telegram responses;
- redaction of known secret shapes/paths as defense in depth;
- no automatic retry of mutations after ambiguous timeout or transport failure.

Long outputs should be summarized or attached as a bounded text artifact only if that path preserves the same secret/output policy.

## 10. Secret-sensitive commands

Even under `/run-ro`, the system should prevent access to obvious secret sources through capability restrictions and mounts rather than merely hiding the resulting text.

Examples that should not be available to the diagnostic sandbox include unrestricted reads of:

```text
.env files containing credentials
process environments of privileged services
~/.ssh
provider credential stores/keyrings
Docker inspect output containing secrets
Runtime/n8n secret mounts
host browser/session credential stores
```

The bot should never provide a generic `env`/`printenv` capability over a privileged process environment.

## 11. WSL / Windows lifecycle

The terminal gateway is local-machine infrastructure. It only processes Telegram updates while the Windows machine and the relevant WSL environment are running.

Recommended first implementation:

```text
Windows login/startup
    -> Task Scheduler or equivalent startup hook
    -> wsl.exe
    -> systemd/user service or supervised daemon
    -> PCP terminal bot long-polling loop
```

If Windows sleeps, powers off, loses network access, or WSL shuts down, Telegram messages may remain unprocessed until the local service is available again. The design must not imply an always-on cloud agent unless one is separately deployed and approved.

## 12. Relationship to PCP trust boundaries

The terminal gateway is an owner convenience surface; it must not collapse existing PCP service boundaries.

In particular:

- developer agents still receive no Docker socket, GitHub merge credential or platform-internal secrets;
- Runtime durable state remains authoritative for coding-job lifecycle/control actions;
- read-only diagnostics do not directly mutate Runtime/PostgreSQL job state;
- `/run-op` uses official bounded control/service interfaces instead of hand-editing database rows;
- no Telegram command may bypass active-job rollout gates, stale-action checks, project/WorkOrder identity checks or production decision boundaries;
- existing PM/Human Owner governance remains unchanged.

The terminal bot itself should not become the place where PM reasoning, model routing, project source of truth or engineering job state is stored.

## 13. Implementation phases

### Phase A — read-only foundation

Build first:

1. separate Telegram bot identity/token;
2. owner/private-chat authentication;
3. long-polling daemon on WSL;
4. `/run-ro` request/preview/result flow;
5. capability-restricted read-only runner;
6. timeout/output/audit controls;
7. no privileged secrets, Docker socket or write mounts.

Exit criterion: the Human Owner can paste a normal multi-line PCP diagnostic block adapted for the read-only runner and receive bounded output without granting mutation authority.

### Phase B — PCP read-only broker

Add:

1. job/plan/action/event/quota inspection API;
2. bounded log inspection;
3. project Git read methods;
4. optional SELECT-only database principal/views;
5. helper CLI/API such as `pcp inspect ...` / `pcp-ro-python` so future ChatGPT diagnostics can avoid `ddev exec` for read paths.

Exit criterion: the common diagnostics currently requiring Runtime-container execution can be expressed without exposing Runtime credentials or a mutable database connection to the Telegram-run script.

### Phase C — Telegram-ready block ergonomics

Add optional support for:

- `PCP-EXEC`;
- `PCP-TTL`;
- `PCP-ID`;
- displayed block hash;
- preview/confirm UX;
- clear distinction between ordinary chat-provided terminal blocks and explicitly requested Telegram-ready blocks.

Exit criterion: when the Human Owner explicitly asks for a Telegram-ready diagnostic block, ChatGPT can provide a deterministic format the bot recognizes directly.

### Phase D — bounded operational actions

Only after the read-only path is stable, add `/run-op` named operations with:

- explicit confirmation;
- fresh state revalidation;
- idempotency/replay protection where applicable;
- one-time operation identity;
- official Runtime/service APIs;
- no generic elevated shell.

Exit criterion: a small approved set of local PCP operations can be executed remotely without bypassing the same safety gates used at the terminal.

### Phase E — reassess need for any higher authority

Do not implement generic `/run-admin` unless a concrete repeated operational need justifies a separate ChangeProposal/security review.

## 14. Explicit non-goals

The first implementation is not intended to provide:

- an unrestricted remote shell;
- remote root access;
- arbitrary Docker administration;
- arbitrary Git writes/pushes;
- database administration;
- production deployment;
- secret browsing;
- an agent that executes every Telegram message as code;
- a replacement for PCP Runtime state machines or governance;
- a requirement that all future read-only blocks use Telegram formatting.

## 15. Documentation and implementation gate

This document records the approved target design and interaction convention only.

Implementation must still follow the normal project workflow:

```text
issue
  -> bounded WorkOrder/design review as appropriate
  -> ai/* branch
  -> deterministic tests
  -> PR
  -> required review/CI
  -> PM merge when eligible
  -> Human Owner controlled local rollout
```

Any implementation choice that materially changes authentication, trust boundaries, host privilege, credential placement, production policy, or introduces a major new service/dependency must be reviewed against the Constitution/Architecture decision boundaries before merge.
